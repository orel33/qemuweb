# Tests

Run commands from the repository root. `./scripts/run-tests.sh --list` shows the available scenarios and prints a short reminder when one starts. `npm test` selects only `test/unit/*.test.js`; the integration scripts must be run explicitly. The integration tests start their own QemuWeb server and guests, then remove the hosts and switches they created.

### Manual check of a VirtualBox host

VirtualBox 7.1 and QEMU/KVM cannot run at the same time: stop every QEMU host (and any other KVM program) first, and use a session whose engine is VirtualBox (**General Settings**). Log in on a runner that has `VBoxManage` (its start-up table shows `✓ VirtualBox`). Then:

1. **Start.** Add a host, system **Alpine Linux** (then **Debian 13 Legacy**), press **Play**: the state goes to *VirtualBox · … starting…* and then running, the Log shows the `$ VBoxManage …` commands in order (`createvm`, `modifyvm`, `createmedium`, `storagectl`, `storageattach`, `modifyvm`, `startvm`), and no `# …` explanation line.
2. **Serial console.** Open the **Console** view: the login prompt appears and typing works (a VirtualBox host has a single console).
3. **Network.** Add a switch `lan` and two VirtualBox hosts connected to it, start all, give them addresses (`ip addr add 10.0.0.1/24 dev eth0`, `10.0.0.2/24` on the other) and `ping` from one to the other.
4. **Refusals.** With a QEMU/KVM host of the SAME session running, press **Play** on a VirtualBox host: a dialog "Cannot start <host>" opens at once, naming your QEMU host(s) to stop (OK or Esc closes it, focus returns to Play), the host's Log has the same sentence, and `VBoxManage list vms` shows nothing new. With only a QEMU/KVM host of ANOTHER session running (another account), the dialog and the Log say only "The virtualization hardware (KVM) of this runner is busy: try again later." with no name; with both, your own hosts are named followed by "or try again later". The reverse: with a VirtualBox host running, a QEMU/KVM start is refused the same way. **Resume all** with several failing hosts opens ONE dialog listing each host (identical sentences grouped), never several dialogs.
5. **Stop, Reset, Remove.** Stop the host (graceful, then Play resumes), Reset it from the base image, then remove it with its **×**.
6. **Nothing left.** After removing every host, `VBoxManage list vms` and `VBoxManage list hdds` list nothing of QemuWeb (no `qemuweb-…` machine, no `disk.vdi` of the runtime directory), and the base images in `images/` are all still present.
7. **A failure.** To see an explained failure, hold KVM with a QEMU/KVM host started by hand, then press **Play** on a VirtualBox host: the Log shows `# VirtualBox cannot start: another program on this machine holds the virtualization hardware (KVM)…`, then the original `VBoxManage: error: … (VERR_VMX_IN_VMX_ROOT_MODE)`, the same sentence in the "Cannot start" dialog, and `list vms` / `list hdds` stay empty.

Status of a VirtualBox host: with the engine VirtualBox, start two hosts (and a switch) and run `./scripts/status.sh`, then `-w` and `--details`, and compare with a QEMU session. The runner shows the hosts as `host (vbox)` under their session (account, node name, system, pid of `VBoxHeadless`, memory in use over the configured memory, CPU %), counted in the session line (`2 hosts, 1 switch · … MB / … MB`), switches as for QEMU; start one of your own unrelated VirtualBox VMs: it never appears. Stop a host: its line disappears, like a QEMU host. `./scripts/killall.sh --dry-run` lists `VirtualBox: qemuweb-…` for the same VMs and nothing else.

Engine select (VBX02): open the app: the header shows `Engine:` and a select on the line of QemuWeb and BETA (same baseline, quieter than the title); General Settings has no engine any more. (1) Add two hosts (one Alpine, one Debian Legacy), start one: the select is frozen (hover: "Stop all hosts to change the engine"); stop it: the select unfreezes at once. (2) With the hosts stopped choose VirtualBox: names, network and startup files stay; a host without a `.vdi` is named in a message ("…: no VirtualBox image on this server"); Host Settings shows "These settings are for VirtualBox; the QEMU - KVM settings of this host are kept separately." Edit memory under VirtualBox, switch to QEMU: the QEMU values are unchanged; back to VirtualBox: the edited value is there. (3) Start a host under each engine in turn (stop between), type something in each, Save with **Include working disks**: the dialog says "QEMU and VirtualBox disks are both included.", the ZIP holds `disk.qcow2` and `disk.vdi` (`unzip -l`); Load it back: the header shows the saved engine, both disks work after switching. Reset under one engine keeps the other's disk (check `<runtime>/sessions/<id>/<host>/`). (4) A saved VirtualBox disk on a machine where the base `.vdi` was rebuilt: the "base image changed" warning and **Discard working disks**. (5) UNVERIFIED PATH: load a ZIP with a `disk.vdi` under VirtualBox and press Play: the host resumes from the saved disk (`VBoxManage list vms` then shows the machine, `list hdds` its disk). (6) Two tabs: changing the engine in one updates the select, the system list and the hosts in the other; stop-all in one unfreezes the other. (7) An administrator observing a user sees that user's engine in a disabled select; `/admin` has no select. (8) Narrow window (below 640 px): the label disappears, the select stays, the header stays on one line. (9) With only one engine installed the select is disabled.
