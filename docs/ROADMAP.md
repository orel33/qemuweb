# QemuNet to Qemuweb roadmap

This is a draft implementation plan for migrating QemuNet's virtual networks to the browser. The existing single-VM QEMU and VirtualBox demo remains usable throughout. The first network release targets local QEMU on Linux and text-mode Linux guests. Production at CREMI also requires OpenID Connect authentication, isolated sessions for concurrent users, and execution on a remote Linux server. VirtualBox network parity and graphical guests remain later decisions.

## Current `dev` prototype

The first network slice is available in `dev`: create a VDE switch tab, start or stop its process, and send commands such as `help` or `port/allprint` through its management socket. Before a QEMU VM's first launch, add up to four Ethernet interfaces and select a running switch for each. Qemuweb assigns a distinct VDE port and MAC address and includes the corresponding `-netdev vde` and `-device e1000` arguments in the launch command. Stop and resume keep the same interface assignments. VM tabs without a selected switch have no network adapter; VirtualBox networking is disabled. No guest has an external connection.

This slice uses independent switch and VM tabs. The next network milestone is a reproducible two-host LAN with guest IP configuration and a whole-network start/stop action. Live attachment of an already running VM is Stage 8; it needs QEMU monitor hotplug and guest-side verification. Switch, VM and disk state still live only for the current server process.

## Target workflow

1. Sign in for production use, select or provide a topology, inspect the machines and links, and start the whole network.
2. See three tabs for the first LAN: host A, switch `s1`, and host B. Each host tab has its serial console and QEMU monitor; the switch tab has its VDE management console. Follow network-level status and startup errors in one place.
3. Configure guest interfaces, verify traffic between hosts, stop or resume the network, and explicitly discard or save its state. Another user's networks stay separate; one user can own several networks at once.

The first milestone is a **working two-host LAN with a visible switch**: two prepared Linux guests on one VDE switch, with three working browser tabs, can exchange packets over their virtual Ethernet interfaces. The four-host `demo/lan.topo` is the next compatibility target. A switch alone does not configure guest IP addresses; the verification scenario must supply them explicitly or through guest startup scripts.

The switch tab represents the VDE process, not another VM. It shows the switch's running state, connected host interfaces and port numbers, startup log, and an interactive command transcript. Commands such as `help` and `port/allprint` go to the switch's Unix management socket (`vde_switch -M`), as `vdeterm` does in QemuNet's optional `-y` mode. This is separate from both a guest shell and the QEMU monitor. Switching tabs must not start or stop the switch or its hosts.

## Startup discovery and capability checks

The server performs one preflight at startup and exposes its results to the UI. Explicit administrator-configured executable paths take precedence; otherwise it searches `PATH` and optional configured search directories. A user-installed QEMU, for example under `/opt`, is a normal supported case. Paths are server configuration, never arbitrary paths submitted by a browser user. The selected paths are used consistently for checks, image operations and VM launches.

- **Executables and dependencies:** find QEMU, `qemu-img`, `vde_switch` and optional tools required by enabled features; find `VBoxManage` only when VirtualBox is configured. Run lightweight version/help probes with timeouts to catch missing shared libraries and unusable binaries, not just missing files. Check the runtime and image directories for needed access; report missing prepared base images separately by system.
- **QEMU capabilities:** inspect the selected QEMU build for required machine and network backends, especially VDE; inspect `qemu-img` for the formats needed for RAW bases and QCOW2 overlays. Record exact paths and versions. A VDE LAN is unavailable if either QEMU's VDE backend or `vde_switch` is unavailable, while unrelated engines remain usable.
- **Acceleration:** report host CPU virtualization flags (`vmx` or `svm`), `/dev/kvm` presence and permissions, and whether the selected QEMU build can actually use KVM. CPU flags alone do not prove KVM is available. Offer TCG independently when supported; do not silently change a user's KVM selection to TCG.
- **Per-engine result:** check VirtualBox runtime support as well as `VBoxManage`, then publish `available`, `unavailable` or `degraded` with a reason for QEMU/KVM, QEMU/TCG, QEMU/VDE LAN and VirtualBox. Show these results at startup and in Settings, and disable unavailable choices. Recheck capabilities that can change at runtime, such as `/dev/kvm` access or conflicts with active VMs, immediately before launch.

The preflight is a reusable framework, not a record of the current developer machine. Installation and repair guidance should identify the failing component, while an optional missing engine must not prevent the server from serving its other modes.

The first preliminary step is implemented as a strict command check: `.env.local` overrides `.env` and `PATH`, seven named executables receive startup checks, and the server exits if any is unavailable. The later capability report will refine this into per-engine results so optional engines can be unavailable without blocking unrelated modes.

## Delivery order

| Stage | Work | Done when |
|---|---|---|
| 0. Startup discovery and preflight | At server startup, resolve configured tool paths and discover available engines and their dependencies. Probe QEMU/KVM, QEMU/TCG, QEMU/VDE and VirtualBox separately; publish a capability report with the selected executable paths, versions and reasons for unavailable modes. | A user-installed QEMU in a configured path works even if it is absent from `PATH`. A broken executable or missing dependency disables only the affected mode with a clear diagnostic; the interface offers only verified modes. |
| 1. Define the network contract | Specify an internal network model (`network`, `owner`, `switches`, `hosts`, ordered interfaces), its API and ownership of session files. A switch has its own process, management socket, state, log and tab identity. Allow several networks per owner and unique internal IDs independent of user-visible names. Parse a restricted QemuNet `.topo` subset as data: `SWITCH` and `HOST <system> <name> <switch>...`. Validate names, system IDs, switch references, duplicate names and limits before starting any process. Do not execute topology text as shell code. | Valid LAN and two-LAN examples produce the expected graph and stable port/MAC assignments; malformed input starts nothing. The current single-VM flow still works. |
| 2. Network runtime | **Prototype:** individual VDE processes, management commands, QEMU VDE interfaces, distinct port/MAC assignments and stop ordering are implemented. Next, give each network its own runtime directory, start/stop switches and hosts as a unit, handle partial startup failure, and verify two-host traffic with explicit guest IP addresses. | A two-host LAN starts and stops as one unit. Both host consoles work; a management command returns a response from `s1`; the hosts can ping after explicit IP configuration. Repeated start/stop and failed start leave no orphan switches or VMs. |
| 3. Browser workflow | **Prototype:** switch tabs with command input and VM interface selection are implemented. Next, add a network view with topology preview, connected-host/port display, network-level state and log, and whole-network actions. | The two-host LAN is usable entirely from the browser: both serial consoles and the `s1` management console respond, port assignments are visible, and the network can be stopped without using the command line. The existing single-VM workflow remains available. |
| 4. Guest setup and compatibility | Provide a documented way to set hostnames and IPs, initially through an opt-in per-host startup directory mounted by virtio-9p. Map QemuNet system IDs to prepared Qemuweb images; do not assume the old Debian 10 kernel/initrd and the current Debian 13 disk boot are interchangeable. Extend the topology parser only after the basic LAN works. | The four-host demo can boot from supported prepared images with predictable names and IPs; its guest tabs and switch tab work, and the guests communicate without manual reconfiguration each run. |
| 5. Durable network sessions | Separate **Stop** (keep overlays), **Resume** (same overlays), **Reset** (fresh overlays) and **Delete** (remove network files). Persist owner and network metadata alongside the session state, rather than relying only on the server's in-memory map. Add a versioned, explicit export/import format for topology, guest setup and overlays. Validate imported paths and referenced base images. | One owner can stop and resume two independent LANs with their disk changes; an exported LAN can be restored after a server restart and its connectivity still works. |
| 6. CREMI identity and multi-user isolation | Integrate the CREMI OpenID Connect provider with a server-side login session. Derive the stable user key from the validated issuer and subject claims. Scope every network, VM, switch, overlay, console, monitor, log and export to its owner. Authenticate WebSocket connections and authorize each room subscription and command. Define user quotas, concurrent-session limits, logout/expiry behavior and administrator policy. | Two CREMI users can run separate LANs concurrently, and one user can run multiple LANs. Neither user can list, subscribe to, read, command, reset or delete the other's resources by guessing IDs or calling APIs directly. Session expiry blocks further commands according to the agreed policy. |
| 7. Remote execution | Run the Qemuweb backend on one remote Linux server that owns the images, overlays, QEMU and VDE processes, and Unix sockets. Serve the browser UI over the CREMI-approved authenticated HTTPS entry point; relay host serial streams and switch management traffic through that backend. Define storage location, access rights, reconnect behavior and server restart recovery. | From another computer, an authorized user starts the two-host LAN on the remote server, uses all three tabs, verifies host connectivity, and stops or resumes the LAN. No QEMU/VDE socket is exposed to the network; a dropped browser connection does not stop the LAN. |
| 8. Live attachment | Allow a VM to join an already running VDE switch. A newly started VM can connect in its launch arguments; for an already running QEMU VM, add a VDE backend and a virtual NIC through the QEMU monitor. Prepare a suitable hotplug-capable bus at VM startup, track assigned ports/MACs, and keep the topology and UI in sync. Treat removal or replacement of an existing NIC as a separate operation because it can disrupt the guest. | With `s1` and a VM already running, the user attaches a new NIC from the web UI, sees the new guest interface and switch port, configures an IP, and exchanges packets without restarting either process. Unsupported VM configurations report why hotplug cannot proceed. |
| 9. Advanced QemuNet features | Add multiple switches and multi-interface hosts first, then hubs, switch-to-switch trunks, VLAN configuration and selected legacy archive import according to demonstrated use. Define an explicit compatibility list for `.topo` keywords and archive contents. | `twolans.topo` and a chosen routed/DMZ example pass documented connectivity tests; unsupported legacy constructs produce clear errors. |

## Engineering rules for the first LAN

- Keep the current serial path (`guest ttyS0` ↔ QEMU Unix socket ↔ Node ↔ Socket.IO ↔ xterm.js). Give the QEMU monitor its own socket for each host.
- Keep the switch command path distinct (`browser switch tab` ↔ Node ↔ VDE management Unix socket). Send commands directly to that socket, capture responses in the switch tab and network log, and never pass input through a shell. Decide command framing and reconnect behavior by testing the installed VDE management protocol before implementing the bridge.
- Use VDE for the first LAN to reproduce QemuNet's switch and port behavior. Require a successful preflight for the selected engine before creating a network session.
- Connecting a VM at launch to an existing switch and attaching a new NIC to a running VM are distinct operations. The latter uses QEMU `netdev_add` followed by `device_add`; `set_link` only changes link state. Test the chosen NIC and `q35` PCIe root-port layout on the installed QEMU version before exposing live attachment in the UI.
- Make generated QEMU arguments and port/MAC assignments visible for diagnosis. Use argument arrays when spawning processes; accept topology text only through the validated parser.
- Treat a network as the lifecycle boundary. A host failure must be visible without silently deleting the other hosts' disks. A partially created network must be recoverable or cleanly removed.
- Design API and event routing around an owner from Stage 1. The current single-VM demo accepts client-provided session IDs and broadcasts some events globally; those paths must be changed before multi-user deployment. A browser session and a virtual-network session are different objects.
- Keep the web server bound to loopback while it has no authentication. Stages 6–7 add CREMI identity and the approved HTTPS entry point before remote access. The browser must reach only the web API and event stream; Unix sockets and image files stay on the server.

## CREMI production contract

- Confirm the CREMI identity provider's OpenID Connect issuer, client registration, redirect URLs and claims. Use the authorization-code flow with PKCE and validate the returned identity; keep application sessions in secure server-side storage with protected cookies. Do not treat a display name or email address as the stable owner ID.
- Authorize **every** HTTP request and Socket.IO event against the authenticated owner, including session discovery, tab subscriptions, console input, QEMU monitor commands, VDE commands, logs, uploads, exports and deletion. Avoid global broadcasts of user-specific state.
- Give each network an isolated runtime directory and unique IDs for its hosts and switches. Enforce per-user and server-wide limits for VM count, memory, disk and running time so concurrent users cannot exhaust the host.
- Specify whether logout or login expiry merely disconnects the browser or also stops VMs; keep that behavior consistent with session recovery. Record sufficient audit events for ownership and lifecycle diagnosis without recording passwords typed in guest consoles.

## Decisions to settle before implementation

1. Should the first release accept a pasted/uploaded QemuNet `.topo` file, offer built-in examples, or both? A built-in two-host example is sufficient for the runtime milestone; file import is needed for compatibility.
2. Should guest IP setup initially use 9p `start.sh` directories, a prepared image mechanism, or manual commands? This determines how the four-host demo becomes reproducible.
3. When should legacy `.tgz` session import be supported? The proposed order establishes a versioned Qemuweb export first, then imports selected legacy archives with explicit compatibility checks.
4. For remote execution, should the first deployment place the Qemuweb backend directly on the VM host (the proposed simple path), or should a separate central controller manage one or more worker hosts? The first choice supports one remote server; multi-server scheduling can follow later.
5. What are the CREMI OpenID Connect issuer and deployment constraints (registered client, reverse proxy, allowed claims or groups)? This information is needed for Stage 6, but not for the local LAN prototype.
6. What are the expected per-user limits and the policy when a user logs out, a browser disconnects, or a login session expires while VMs are running?

The implementation can begin with Stage 0 while these product decisions are refined.
