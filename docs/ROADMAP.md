# QemuNet to Qemuweb roadmap

This is a draft implementation plan for migrating QemuNet's virtual networks to the browser. The existing single-VM QEMU and VirtualBox demo remains usable throughout. The first network release targets local QEMU on Linux and text-mode Linux guests. Production at CREMI also requires OpenID Connect authentication, isolated sessions for concurrent users, and execution on a remote Linux server. VirtualBox network parity and graphical guests remain later decisions.

## Engine roadmap — project direction

This is the primary engine roadmap for QemuWeb. Keep the execution layer extensible, while implementing and maintaining engines in this order:

1. **QEMU/KVM — primary target.** This is the preferred engine for Linux VMs and VDE-connected LANs. Require KVM when the user selects this mode; report an error if it is unavailable rather than silently changing acceleration.
2. **QEMU/TCG — fallback mode.** Keep it available as an explicit software-emulation fallback for hosts where KVM cannot be used. It is not the preferred routine engine.
3. **VirtualBox — first alternative engine.** Maintain its existing VM support as well as practical, including compatibility with the prepared OS images and lifecycle controls. Keep in mind that its ability to run concurrently with QEMU/KVM depends on host hypervisor constraints.
4. **VMware — future hypervisor.** Preserve room for a future adapter, disk conversion/profile and console integration; do not make it a current implementation target.
5. **Docker / Podman — lightweight VDE terminals, to investigate.** Explore whether a container built from a Dockerfile can act as a lightweight host on a VDE network, alongside full VMs. This is a distinct execution type, not a VM engine: containers share the host kernel and do not boot the Linux kernel stored in our RAW images. This feature must work as an ordinary user: no `sudo`, no host-level `CAP_NET_ADMIN`, no TAP interface or bridge created in the host network namespace, and no host network reconfiguration. A candidate design is a rootless container with its own network namespace, with any required `CAP_NET_ADMIN` scoped only to that namespace, and a VDE plug connecting an interface inside it to the user's VDE socket. Validate the `/dev/net/tun` access, socket permissions and user-namespace requirements on supported hosts. If “all in userland” is intended to forbid even a namespace-scoped TAP device/capability, investigate a user-space Ethernet endpoint instead; make that distinction explicit before choosing the implementation.

The Docker/Podman idea is specifically for small command-line/networking terminals useful in practical labs. It should let a topology mix full QEMU/VirtualBox VMs and container-based terminals on the same VDE switch, without host-level privileges or host network changes. It does not replace the RAW image preparation workflow for VM systems.

## Current `dev` prototype

The first network slice is available in `dev`: create a VDE switch tab, start or stop its process, and use its interactive management terminal. Qemuweb launches `vdeterm` in a server-side pseudo-terminal and relays it through Socket.IO to the tab's xterm.js, reproducing QemuNet's `xterm -e vdeterm <management-socket>` workflow in the browser. A new QEMU VM has one disconnected Ethernet card by default; before its first launch, it can have up to four cards, each left disconnected or assigned to a running switch. Qemuweb gives every card a MAC address and every connected card a distinct VDE port. Connected cards use `-netdev vde` and `-device` at launch; the selected model is `e1000` for Debian 13 Legacy and `virtio-net-pci` for Debian 13 Cloud. Stop and resume keep the same assignments. VirtualBox networking is disabled. No guest has an external connection.

This slice uses independent switch and VM tabs. The next milestone is to prove a two-host LAN with two Debian 13 Legacy guests, one VDE switch and explicit guest IP addresses. A whole-network start/stop action follows that working baseline. Live attachment then adds a new NIC to a running VM through the QEMU monitor and verifies it in the guest. Switch, VM and disk state still live only for the current server process.

### Next LAN checkpoint

1. Start `s1`, then two `debian13-legacy` VMs with their `e1000` cards assigned to `s1` before launch. Check that both serial consoles work and `port/allprint` shows two occupied switch ports.
2. Use `ip -br link` to find each guest's interface name. Configure `192.168.10.1/24` and `192.168.10.2/24` inside the guests, then ping in both directions. VDE supplies Ethernet switching, not DHCP; an automatically assigned `169.254/16` address does not prove connectivity between the guests.
3. Stop and resume both VMs without losing their disks or switch assignments. Record the commands and observed results as a repeatable LAN example before adding whole-network controls or hot attachment.

## Target workflow

1. Sign in for production use, select or provide a topology, inspect the machines and links, and start the whole network.
2. See three tabs for the first LAN: host A, switch `s1`, and host B. Each host tab has its serial console and QEMU monitor; the switch tab has its VDE management console. Follow network-level status and startup errors in one place.
3. Configure guest interfaces, verify traffic between hosts, stop or resume the network, and explicitly discard or save its state. Another user's networks stay separate; one user can own several networks at once.

The first milestone is a **working two-host LAN with a visible switch**: two prepared Linux guests on one VDE switch, with three working browser tabs, can exchange packets over their virtual Ethernet interfaces. The four-host `demo/lan.topo` is the next compatibility target. A switch alone does not configure guest IP addresses; the verification scenario must supply them explicitly or through guest startup scripts.

The switch tab represents the VDE process, not another VM. It shows the switch's running state, connected host interfaces and port numbers, startup log, and an interactive command transcript. Commands such as `help` and `port/allprint` go through `xterm.js ↔ Socket.IO ↔ node-pty ↔ vdeterm ↔ vde_switch -M`, matching QemuNet's optional `-y` mode. The persistent terminal preserves the VDE prompt, line editing, history, completion and asynchronous messages. This is separate from both a guest shell and the QEMU monitor. Switching tabs must not start or stop the switch or its hosts.

### Interactive VDE terminal task — implemented, browser validation pending

1. Replace the command-at-a-time HTTP endpoint and its `<pre>`/input form with the xterm.js already used by VM tabs.
2. Start one `vdeterm` process per running switch inside a server-side pseudo-terminal; keep its lifetime tied to the switch and never interpolate browser input into a shell command.
3. Relay terminal bytes through the selected session's Socket.IO room, retain a bounded transcript for tab changes and browser reconnection, and propagate xterm dimensions to the pseudo-terminal.
4. Stop the pseudo-terminal when its switch stops or is removed, and surface an unexpected `vdeterm` exit as a switch error.

This task is complete when `help`, command history, completion and `port/allprint` work in the browser terminal; changing tabs restores the transcript; resizing the page updates the pseudo-terminal; and stopping the switch leaves no `vdeterm` process behind.

## Startup discovery and capability checks

The server performs one preflight at startup and exposes its results to the UI. Explicit administrator-configured executable paths take precedence; otherwise it searches `PATH` and optional configured search directories. A user-installed QEMU, for example under `/opt`, is a normal supported case. Paths are server configuration, never arbitrary paths submitted by a browser user. The selected paths are used consistently for checks, image operations and VM launches.

- **Executables and dependencies:** find QEMU, `qemu-img`, `vde_switch` and optional tools required by enabled features; find `VBoxManage` only when VirtualBox is configured. Run lightweight version/help probes with timeouts to catch missing shared libraries and unusable binaries, not just missing files. Check the runtime and image directories for needed access; report missing prepared base images separately by system.
- **QEMU capabilities:** inspect the selected QEMU build for required machine and network backends, especially VDE; inspect `qemu-img` for the formats needed for RAW bases and QCOW2 overlays. Record exact paths and versions. A VDE LAN is unavailable if either QEMU's VDE backend or `vde_switch` is unavailable, while unrelated engines remain usable.
- **Acceleration:** report host CPU virtualization flags (`vmx` or `svm`), `/dev/kvm` presence and permissions, and whether the selected QEMU build can actually use KVM. CPU flags alone do not prove KVM is available. Offer TCG independently when supported; do not silently change a user's KVM selection to TCG.
- **Per-engine result:** check VirtualBox runtime support as well as `VBoxManage`, then publish `available`, `unavailable` or `degraded` with a reason for QEMU/KVM, QEMU/TCG, QEMU/VDE LAN and VirtualBox. Show these results at startup and in Settings, and disable unavailable choices. Recheck capabilities that can change at runtime, such as `/dev/kvm` access or conflicts with active VMs, immediately before launch.

The preflight is a reusable framework, not a record of the current developer machine. Installation and repair guidance should identify the failing component, while an optional missing engine must not prevent the server from serving its other modes.

The first preliminary step is implemented as a strict command check: `.env.local` overrides `.env` and `PATH`, seven named executables receive startup checks, and the server exits if any is unavailable. The later capability report will refine this into per-engine results so optional engines can be unavailable without blocking unrelated modes.

## Engineering rules for the first LAN

- Keep the current serial path (`guest ttyS0` ↔ QEMU Unix socket ↔ Node ↔ Socket.IO ↔ xterm.js). Give the QEMU monitor its own socket for each host.
- Keep the switch terminal path distinct (`browser xterm.js` ↔ `Socket.IO` ↔ `node-pty` ↔ `vdeterm` ↔ VDE management Unix socket). Relay bytes directly between xterm.js and the pseudo-terminal; never pass browser input through a shell. Keep a bounded transcript for reconnection and propagate terminal resizing.
- Use VDE for the first LAN to reproduce QemuNet's switch and port behavior. Require a successful preflight for the selected engine before creating a network session.
- Connecting a VM at launch to an existing switch and attaching a new NIC to a running VM are distinct operations. The latter uses QEMU `netdev_add` followed by `device_add`; `set_link` only changes link state. Test the chosen NIC and `q35` PCIe root-port layout on the installed QEMU version before exposing live attachment in the UI.
- Make generated QEMU arguments and port/MAC assignments visible for diagnosis. Use argument arrays when spawning processes; accept topology text only through the validated parser.
- Treat a network as the lifecycle boundary. A host failure must be visible without silently deleting the other hosts' disks. A partially created network must be recoverable or cleanly removed.
- Design API and event routing around an owner from Stage 1. The current single-VM demo accepts client-provided session IDs and broadcasts some events globally; those paths must be changed before multi-user deployment. A browser session and a virtual-network session are different objects.
- Keep the web server bound to loopback while it has no authentication. Stages 7–8 add CREMI identity and the approved HTTPS entry point before remote access. The browser must reach only the web API and event stream; Unix sockets and image files stay on the server.

## CREMI production contract

- Confirm the CREMI identity provider's OpenID Connect issuer, client registration, redirect URLs and claims. Use the authorization-code flow with PKCE and validate the returned identity; keep application sessions in secure server-side storage with protected cookies. Do not treat a display name or email address as the stable owner ID.
- Authorize **every** HTTP request and Socket.IO event against the authenticated owner, including session discovery, tab subscriptions, console input, QEMU monitor commands, VDE commands, logs, uploads, exports and deletion. Avoid global broadcasts of user-specific state.
- Give each network an isolated runtime directory and unique IDs for its hosts and switches. Enforce per-user and server-wide limits for VM count, memory, disk and running time so concurrent users cannot exhaust the host.
- Specify whether logout or login expiry merely disconnects the browser or also stops VMs; keep that behavior consistent with session recovery. Record sufficient audit events for ownership and lifecycle diagnosis without recording passwords typed in guest consoles.

## Decisions to settle before implementation

1. Should the first release accept a pasted/uploaded QemuNet `.topo` file, offer built-in examples, or both? A built-in two-host example is sufficient for the runtime milestone; file import is needed for compatibility.
2. The immediate two-host checkpoint uses manual static IP commands. For the later four-host demo, should guest setup use 9p `start.sh` directories or a prepared image mechanism?
3. When should legacy `.tgz` session import be supported? The proposed order establishes a versioned Qemuweb export first, then imports selected legacy archives with explicit compatibility checks.
4. For remote execution, should the first deployment place the Qemuweb backend directly on the VM host (the proposed simple path), or should a separate central controller manage one or more worker hosts? The first choice supports one remote server; multi-server scheduling can follow later.
5. What are the CREMI OpenID Connect issuer and deployment constraints (registered client, reverse proxy, allowed claims or groups)? This information is needed for Stage 7, but not for the local LAN prototype.
6. What are the expected per-user limits and the policy when a user logs out, a browser disconnects, or a login session expires while VMs are running?

The immediate work is the Stage 2 two-host checkpoint, with Stage 0 capability discovery continuing alongside it.
